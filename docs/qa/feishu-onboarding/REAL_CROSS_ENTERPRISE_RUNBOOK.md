# 飞书跨企业真实闭环 · 5 分钟验证手册（FL-D788 销号脚本）

> 触发条件：用户提供**第二个飞书企业**的账号（该企业内是管理员，或管理员在场协助）。
> 目标：证明「企业外用户 → 自建应用 → 长连接 → 绑定 → 私聊 DOCX 出结果」真实可用，并留下可入册证据。
> 原则：全程只用产品页面（工作台/飞书开放平台/飞书客户端），不用任何开发者脚本；凡是动用脚本/命令的只用于「取证」，不替代用户路径。

## 0. 开始前准备（30 秒，验证人自查）

- [ ] 拿到：第二企业的飞书账号（手机已登录该企业）+ 该账号在 FundLex 的登录账号。
- [ ] 生产地址可访问：工作台能登录；左栏「飞书绑定」可打开。
- [ ] 预开取证窗口（运维只读）：`sudo journalctl -u fundlex-recall-worker -f`（验证 Secret 不出现在日志）。

## 2. 验收点（全部满足才可销 FL-D788）

1. 全程无报错页、无「不是一个企业」；失败时显示的是人读诊断码+修复链接而不是技术栈错误。
2. **路由正确性（核心）**：所有机器入回复都来自**第二家企业自己的应用**（机器人头像是该企业应用的），不是部署方机器人。
3. 服务端取证（运维）：
   - `feishu_apps` 表出现 1 行：`tenant_key`=第二企业租户、`status=active`、`first_event_at` 有值；Secret 列只有密文（`gAAAAA` 前缀）。
   - `journalctl -u fundlex-recall-worker` 仅含 app_id/错误类型，**零凭证**。
   - `GET /api/integrations/feishu/app`（该用户身份）响应不含 Secret 明文。
4. 业务闭环：私聊 DOCX → 处理 → 结果链接 → 授权下载，修订文件实际产生且与报告一致。

## 3. 失败分支速查

| 现象 | 处理 |
| --- | --- |
| 保存报 `FEISHU_APP_CREDENTIALS_INVALID` | App ID/Secret 不匹配或 Secret 已重置；重复制重贴 |
| 一直「正在建立连接…」 | 回第 3 步：订阅方式必须是「长连接」、已加 `im.message.receive_v1`、版本已发布且审核通过 |
| 机器人搜不到 | 机器人能力未启用或版本未发布 |
| 权限一直「待验证」 | 未授 `application:application:self_manage`，属正常；以收到消息为准，不阻塞 |
| 绑定码过期 | 点「换一个」再发 |
