# FundLex 当前方案多 agent 讨论

日期：2026-10-14。性质：设计审查及交叉讨论，未实施、未调用业务模型、未进行质量或性能评测。

参与：召回与业务 agent、工程与 DOCX agent、评测与交付 agent。三方先独立审查设计及原件阅读记录，再交换质疑并收敛结论。下文共识表示审查意见，不代表用户已批准新增决策，也不是业务准确率证据。

## 1. 本轮审查基线

以最近对话为准：默认内置指引，上传/启用仅配置页；代码拆分章、节、段落及表格并保留地址；模型映射规则到业务子节，深读相关子节及事实和摘要；没有找到和覆盖不足时扩展搜索；已有命中的规则仍查漏；复核问题自动补证、修复与仲裁，未解决才记未完成；模型参考当前产物和原件修复完整方案，代码每轮从原始合同重新生成。

草案与口头表述存在待统一处：草案要求原件及最终产物强制全文扫描，近期讨论提出不默认全文深读、必要时全文查漏；草案还未完整表达原件重生成的双地址和依赖失效契约。本轮只记录建议，不静默将某一版本视为已批准。

## 2. 三方一致支持

- 代码负责物理结构和地址，模型负责业务范围与语义判断。
- 章作导航，业务子节或完整逻辑条款作深度阅读与修订单元。
- 结合收费事实、跨段关系、正文和摘要位置，不只读关键词附近几句。
- 多规则重叠由模型联合规划，不用固定优先级裁掉要求。
- 从原件重放更新后的完整方案，避免修订叠加与来源地址漂移。
- 对真实生成文件复核，自动修复与仲裁，未完成明确记录。

## 3. 核心挑战与交叉结论

### A. 无异常信号时，条件补扫如何发现未知遗漏？

召回和评测 agent 都提出：规则命中一处、映射看似齐全时，另一处未映射目标可能没有任何触发信号。工程 agent 认可覆盖账本只能证明读取任务完成，不能证明模型语义发现齐全。

推荐默认“相关业务子节深读＋最终实际产物一次轻量全文查漏”。轻量指全部原文分块读取、仅做遗漏发现，不是只看标题、摘要，也不是逐段深度改写。所有块都有相关业务要求，不能用初次映射过滤最终搜索范围。

中间补证与修复按影响范围执行；最终查漏发现新目标则回到修复，并重新检查最终新版本。达到上限时记未完成。

这是本轮新增建议，尚非用户已确认要求。无需默认每个阶段都反复深读全文；同时不能把条件搜索表述为绝无漏改保证。

### B. 从原件重生成后，如何修复产物中新发现的问题？

工程提出双地址体系：来源地址固定绑定原件，每轮产物地址绑定该产物；实际产物内容关联原件范围或生成操作。

- 原文残留问题：回到原件范围，新增或调整目标。
- 生成文字错误：更新产生该文字的修订操作。
- 缺失义务：根据规则依据选择来源插入锚点。

不能把新产物字符位置直接用于旧原件；实际读取新DOCX并核对映射，不以计划文字替代文件内容。跨段理解不要求合并段落，可拆成多个精确文字操作；删除段落标记、合并段落和改变表格结构作为独立结构能力验证。

### C. 已通过的修改是否始终能保留？

三方同意复用未受影响的方案，但新收费事实、类别机制或相关条款可能使旧方案失效。需记录规则、事实、来源块、目标及正文摘要依赖；依赖变化重新判断关联结果。重大画像变化再安排模型影响分析，检查未记录的依赖。

保留通过的方案不等于保留旧文件验收。每个新组合生成后，对新的实际文件做一致性与覆盖检查，不能将不同文件的通过记录拼成最终验收。

### D. 什么才算覆盖与完成？

评测要求区分：

1. 结构覆盖：全部可读部件是否提取、扫描。
2. 规则处置覆盖：每条规则及其类别、渠道、期限、位置是否有明确处置。
3. 业务召回：独立标签中的应改目标实际发现多少。

前两项不能代替第三项。目标被编辑也不等于义务正确落实。主指标应是应改目标正确完成率和整份合同全部应改目标完成率，资格误排、不可编辑目标、未知及扫描缺口均纳入端到端统计。

规则的旧文示例缺失，不自动要求补写；摘要不机械复制正文；已满足允许不同措辞。业务标签先明确条件性替换/删除、明确追加与整体义务。

### E. 如何避免指引解析的共同盲点？

召回提出独立指引对账：来源业务组 → 原文/新文 → 条件/引用/互斥分支 → 规则。解析核验先独立阅读来源形成期望要求，再对照解析结果，不能只检查JSON格式或只用生成规则验收生成规则。

“同前述说明”必须解释关联，颜色辅助理解但不充当唯一语义。指引解析质量与合同处理质量分别用独立标签验收。

## 4. 工程补充约束

- 可读和可写分开，不可编辑内容也应进入发现账本。
- 输出截断、分页未完、跨窗口条款、未读内容均可见，不能只信模型finished=true。
- 每轮绑定原件、指引、事实、方案和产物版本，使用临时产物及幂等提交；迟到答复和过期Worker不能覆盖新版本。
- 接受全部修订等价于final，拒绝全部修订恢复source内容；对明确的必要元数据差异另行声明。验证未授权范围、编号、域、书签、关系和表格，必要时抽样渲染。
- Word可以逐条接受拒绝，但正文摘要等依赖修改应标识联合取舍，不能承诺任意回退组合仍业务一致。

## 5. 推荐收敛流程

代码结构提取 → 模型映射业务子节及提取事实 → 子节完整盘点 → 联合修订 → 原件重生成 → 实际文件局部复核与自动修复 → 方案收敛 → 最终分块全文查漏及业务一致性检查 → 分级交付。

发现最终遗漏时回到目标/方案修复；新版本重新验收。全过程保留原文、来源规则、修改、事实依赖及复核证据。

## 6. 尚需实测的取舍

三方没有原则性分歧。需验证：

- 条件补扫与默认最终轻量全扫的召回收益、费用和耗时差异。
- 额外规则视角搜索及不同审计模型是否降低共同盲点。
- 长合同窗口、业务包与并发的合适规模。
- 跨段、表格及复杂修订单元的实际可执行能力。

采用冻结的独立分层标签，比较条件补扫、最终轻量全扫及额外规则视角搜索。报告新增正确目标、错误修改、整合同完成率、调用/token/费用及p50/p95耗时。没有真实证据时，不断言8次调用或95%门槛可用。

推荐固定执行原则：模型参考当前产物修复完整方案；代码从原始合同重建；旧方案按依赖复用，新文件重新验收。
