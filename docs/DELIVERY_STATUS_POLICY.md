# 交付状态与例外清单政策（v2 正式交付）

日期：2026-10-14。适用于 auto_write 开启后的正式交付（delivery 模式）。

## 1. 状态定义

| 状态 | 含义 | 是否发布合同文件 |
| --- | --- | --- |
| `complete` | 所有适配动作全部执行并通过校验 | 是（`final.docx` + `redline.docx`） |
| `complete_with_exceptions` | 已执行的修改全部通过校验；存在未自动修改的条款（例外清单） | 是（附例外清单） |
| `incomplete` | 没有任何已执行修改，且存在失败动作（无可交付内容） | 否 |
| `not_generated` | 处理流程失败，未生成产物 | 否 |

评测模式对应状态：`evaluation_modified` / `evaluation_modified_with_exceptions` / `evaluation_unmodified` / `incomplete` / `not_generated`。

## 2. 为什么"有例外仍发布"

v2 引擎中**任何 `failed` 都是失败关闭**：证据不足、原文与指引旧文不一致、模型引用核对失败等情况下，引擎从不会写入。已执行修改则必须通过服务端记录校验、修订等价与非目标校验后才进入产物。

因此：
- 发布已校验修改 + 显式例外清单，业务能拿到可用合同并精确知道哪些条款需人工处理；
- 全部扣留会让"一处证据不足"阻断整份合同的交付，不符合实际业务使用；
- 唯一仍然"不发文件"的情形是：**没有任何修改可交付**（零修改且存在失败动作），避免把未修改的原样文件伪装成交付物。

## 3. 例外清单的呈现

- 报告字段 `report.exceptions`：`[{action_id, reason, description}]`，与逐动作状态一致；
- 工作台任务详情显示"例外清单"区块；结果列表按 `complete_with_exceptions` 排序紧随 `incomplete` 之后、突出需人工处理的合同；
- 人工处理建议：按 `reason` 定位条款后手工修改，或补充证据后重跑（重跑幂等）。

## 4. 与发布门槛的关系

本政策不改变发布门槛：`rules/release_v2.py` 仍要求每个动作的确定性审计（正/反例）全过、零错误写入；交付分级只影响"已发布后的单份合同交付呈现"，不影响发布证据。
