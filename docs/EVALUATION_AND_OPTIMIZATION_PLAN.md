# FundLex 真实修改评测与优化闭环

日期：2026-10-14。用户要求补充：用20—30份合同进行真实修改，计算指标，再根据结果优化。本文件是执行规格，尚未选定实际样本、冻结标签或运行新引擎评测。

## 1. 范围与目的

评测必须真实调用模型、执行DOCX修改并检查实际产物，用于发现指引解析、事实画像、定位、盘点、生成、执行和复核的缺陷。不能只评分诊断、候选清单、计划文字或模型自报结论。

推荐28份不同原件：20份开发评测，8份留出验收；允许在20—30份范围内依据业务覆盖调整，运行前固定。重复运行不增加独立合同数量，所有尝试仍计入调用、费用及时间。

该阶段是质量改进流程，不代替发布后普通工作台正式交付和云端验收。发布前通过qualification通道取得真实修改证据；发布后另验正式用户路径。

## 2. 样本选择、分层与隔离

不只选最容易修改的合同。覆盖：单类别、多类别及陌生字母、不同收费组、QDII币种、浮动管理费、旧式结构、长合同、正文摘要、跨段、合段/公式、已满足、排除及证据冲突。结构边界故障可另用夹具补充，不能替换28份真实原件。

建议20份开发集以实际应改合同为主，可按16份应改、2份已满足、2份应排除组织；8份留出可按6份应改、1份已满足、1份排除组织。若一份同时覆盖多类可复用其层级标签，不要求制造不存在的样本类别。最终分层和数量写入manifest。

必须参考本轮已读的典型合同，但不固定样本白名单或按文件名实现分支。额外使用新抽样原件覆盖未观察的写法。

样本manifest记录匿名case_id、原件路径/hash、长度、结构、事实/业务层级、dev/holdout、历史是否评过、选择理由。留出不参与提示、规则策略、阈值或代码优化；不提前读取其新引擎预测来调优。

从历史评过的514份中抽样时，明确“本轮留出”与“从未见过”不同；同基金近重复版本或高度同文尽量分在同一组，避免开发/留出互相泄漏。

发布前如必须为留出失败修复系统，保留旧结果，记录留出已被用于开发；修复后原留出可按冻结标签复测，但只能称历史留出回归。推荐28份初始选择之外最多预留2份新合同，使本轮唯一原件不超过30；这2份只能报告小规模新样本验证，不能冒称重新取得独立8份验收。如果需要全新的较大留出集，说明新增范围和预算取得相应授权，不偷偷扩样。没有剩余独立样本时如实报告评测局限，绝不改标签或把已看过结果称未见。

## 3. 独立标签先于预测

依据指引与原始合同标注资格、收费事实、规则义务、所有应改目标和原文位置、已满足/不适用依据、可接受新文语义及不可改事实。正文与摘要分别标注，目标按实际对象/类别/渠道/期限区分。

标签包含是否仅条件性改旧文、是否明确必须追加、以及缺失时是否需新增，避免把示例未出现一律当漏改或需补写。

独立模型可辅助初标，须盲读原件和指引，不能看到被评估引擎的结果；不能让修订模型自评充当唯一真值。对关键事实、争议修改和未标注新发现作独立核对，真实业务授权疑义才请用户裁定。

样本、标签、评分口径、阈值、预算和引擎/指引/提示/模型传输版本在运行前冻结并保存hash。已有历史gold保留，新增标签另建版本，不能见预测后修改旧真值以“通过”。

未确认标签单列，不偷偷从总量消失。样本如无法形成可信真值，运行前替换或明确其只作探索，并计入覆盖限制；不能把探索结果宣传为准确率。

## 4. 指标与分母

设G为全部有独立确证的应改目标，包含真实适用但被引擎误排、拒绝、未执行或因结构无法修改的目标；不能在评分时只保留实际成功进入引擎的目标。

目标匹配按冻结的原件地址、业务义务及对象判断，不要求修改边界逐字等于标签，也不能用任意文字变化算正确修改。合理扩大范围须检查额外变化是否有依据。

| 指标 | 计算与含义 |
| --- | --- |
| 目标发现召回率 | G中正确定位到的目标数 / G总数，衡量发现能力 |
| 目标正确完成率（主指标） | G中在最终实际DOCX正确落实全部对应要求的目标数 / G总数 |
| 漏改率与漏改数 | 1－目标正确完成率，并分列未发现、已发现未执行、改了但未正确落实 |
| 整合同全部完成率（主指标） | 全部必需应改目标正确且无未解决重大问题的合同数 / 确证有应改目标的合同数；包括误排及结构失败合同 |
| 按规则完成率 | 每规则正确完成目标 / 该规则确证应改目标；同时给样本支持数，无样本不标100% |
| 修改正确率 | 实际语义修改单元中有规则依据且正确的单元 / 全部实际修改单元；单元划分在评分前固定，不混用字符、操作或action数 |
| 额外修改 | 分列合理范围扩大、已满足再编辑、重复添加、无依据修改与重要余文丢失，不合并成一个“多改”数字 |
| 资格与画像质量 | 错排/错放数；事实关系按独立确证字段正确率、未知率、冲突率；类别/币种/费用机制单列 |
| 执行与审计质量 | 技术校验失败数、审计正确发现及误拒数、修复前后新增完成目标、修复引入错误数 |
| 实际交付质量 | 系统标complete却仍有已确证漏改/错误的合同数（错误完整声明）；工作台上传到下载成功率及hash一致性 |
| 性能与成本 | 每份和全批逻辑调用、HTTP尝试、token、估计费用、重试/修复轮次、p50/p95耗时、峰值内存；开发全部尝试与最终单轮分别报 |

至少同时报告计数和比率，按长合同、复杂结构、收费类型分层。28份样本规模小，结果是受控样本证据，不外推成任意合同不漏改的保证。

没有实际产物的应改目标记未完成；服务阻塞保留部分结果并报“本批未完成”，不能排除失败样本后宣布全批完成率。人工改文件补齐不算引擎完成。

## 5. 评分必须检查文件

从原件与实际下载/保存的最终产物对照，检查每个标签目标的新义务和旧条件消除、类别关系、原费率/公式/条件保留、正文摘要、未标注差异及修订等价。

代码负责重读DOCX、来源/地址/hash、精确字串与结构属性；独立评审判定语义正确。不得只读report.applied或plan.replacement评分。范围差异和新发现目标明确裁定，不能自动全部视为对或错。

生成报告反向与实际文件对账：目标宣称已改但文件无对应变化是错误；文件出现未记录变化同样是问题。

## 6. 优化循环

### 第一步：先用开发集中的1—2份打通

真实模型、队列、实际文件和评分器都走通。它们属于20份开发集，不额外虚增样本。未通过文件与评分核对先修链路，再跑批量。

### 第二步：冻结初版，跑20份开发基线

保存完整原始结果及版本，不遇到错误就覆盖旧目录。先按指标找到错误热点，再逐项分析。

### 第三步：按原因修复，不按样本名打补丁

| 错误类别 | 主要优化方向 |
| --- | --- |
| 指引漏组或条件错 | 来源分组/引用/互斥条件理解及独立解析核验 |
| 资格或收费事实错 | 扩大证据、条件时态和多维关系核对，影响依赖失效 |
| 子节/目标漏找 | 结构歧义、业务映射、完整上下文、跨段盘点、补扫/最终查漏 |
| 新文错误或重复 | 来源授权、槽位、已满足判定、联合规划和衔接 |
| 余文被吞或执行失败 | 语义边界、跨段操作、地址映射、结构能力和技术校验 |
| 审计误拒或漏检 | 实际产物证据、检查要求、独立查漏上下文及修复/仲裁策略 |
| 费用/耗时过高 | 子节大小、分页、依赖缓存、调用合并；同时检查召回是否下降 |
| 前端或下载失败 | API状态/版本、鉴权、上传回执、过期请求、产物下载门禁 |

每个缺陷登记FL-D编号、case/目标、原因证据、处理策略、预期改善及验证；修复补必要的可重复小夹具，避免只写镜像实现测试。

### 第四步：先局部复测，再全开发集回归

修复后先重跑失败目标/合同，确认原因被修复；形成一批改动后冻结新版本，完整重跑20份，检查旧正确目标是否退步、新事实是否破坏无关规则。即使只有少量合同重跑，最终发布证据必须属于最终冻结版本。

建议最多3轮计划内优化，轮次受当前授权预算约束；未达标不默默停下宣称完成，列出剩余缺口并决定有依据的下一轮或明确外部阻塞。

### 第五步：冻结后跑8份留出

仅在开发集达注册门槛且版本稳定后评估留出。完整真实修改和文件评分，报告开发与留出分别结果。留出失败保留记录；若据其调优，该批成为回归材料，按§2记录历史回归和新样本配额，不继续称独立验收。不能因保持留出名义而放任已知错误不修复。

### 第六步：发布后正式端到端与云端复验

取得版本发布资格后，从普通任务提交页重跑真实用户用例并核对下载。可以用已评过合同，但明确是链路复验，不冒称新增泛化数据。至少包括正常应改、长合同、边界状态、配置切换及恢复；云端亦须真实验证。

## 7. 达标、停止和预算

运行前在实施计划登记每指标门槛、样本分层、可编辑正常必需用例、已知结构边界及严重错误定义。最低要求沿整合开发文档§10：无已知严重政策/事实错误、必需目标漏改或错误complete，规定正常可编辑用例全部正确完成；结构/故障边界状态真实，不从主指标分母删掉。

95%之类的平均指标可作开发趋势，不能因达到平均值就接受已知应改目标漏掉。无法支持的真实结构明确列未完成及覆盖边界，不自称业务完整。

优化应看召回与正确完成是否提高，也看重要余文/事实错误、稳定性和成本是否退步。任何质量-成本调整先登记理由，不能只减少调用换取未知漏改。

20—30份是范围授权，不是无限模型调用或费用授权。核对现有账本和环境，估算每轮、最坏重试、修复与留出开销，登记本轮及总cap；所有agent共享账本。任何上限触发暂停、保留断点，不能重置费用或跳过审计。

## 8. 文件和报告产物

建议运行资料在 `var/recall-first-evaluation/<run-id>/`，评分脚本在 `tools/evaluation/`，汇总在 `docs/REAL_REVISION_EVALUATION_RESULTS.md`（接续agent运行后创建，不能现在填通过结果）。

每轮保存manifest、labels/freeze hash、run_context、调用账本摘要、逐合同报告、plan、实际final/redline或明确验证工作文件、hash、target_scores、unlabelled_diffs、metrics和error_analysis。每次新目录，不覆盖旧结果，原件与gold不改。

对比表至少包含版本、开发/留出、已确证目标数、发现数、正确完成数、整合同完成数、错误/未完成类型、费用和耗时；修复前后关联同一目标，不把标签变动当性能提升。

实施阶段创建可重复的选择/冻结、任务运行、产物评分、错误汇总与版本比较工具。前端依旧展示真实任务和结果；研究评测工具不是普通用户额外入口，不替代项目交付。
