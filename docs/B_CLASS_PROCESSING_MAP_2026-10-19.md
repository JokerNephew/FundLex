## 0. 处理原则（先读）

1. **"改动什么"由 Guide + Verified Facts 决定**：报告里的"业务含义偏差"必须先转化为 **Policy Components**（must_add / must_remove / must_preserve）才进入修改流程；
2. **产出方式由 Strategy Router 决定**：T1 模板 → T2 最小编辑 → T3 模型融合（前置条件不满足则降级；事实不确定不降级，回核实）；
3. **授权外一律不动**：V2 用"授权窗口外精确一致"兜底——**报告中的多数"差异形态"因此只影响定位与组件设计，不再需要逐形态裁定"算不算 B 类"来指导引擎**；
4. 一切修改由 V1/V2/V3 + Coverage Ledger 证明；未过门 → unresolved（禁止 complete）。

## 4. 收敛结论（哪些还悬着）

实施 v2 后，B 报告的候选形态在引擎侧**绝大多数不再需要"先裁定算不算 B 类"**——行为由"授权组件 + T1/T2/T3 + V1/V2/V3"直接决定。真正仍悬着的收敛为三类：

**A. 仍需业务裁定（决定"该不该改/算不算满足"，共 8 项）**
1. G11-1 认购/申购环节错位（455 份）；
2. Q2/§39.2："按收费性质"扩展到 G11/G14/G16 的范围；
3. G14-4 笼统"销售费率"是否强制分项；
4. 第 12 项：G15 删除后是否还需"按指引时限/路径整改"（方案答：否，G16 提供新政策）；
5. G16-2 / §39.3："每日计算、逐日累计"是否等同"每日计提"；
6. Q3/M6：货币基金（8 份）是否在范围内；
7. Q4/Q5：G14 "已含销售服务费"与"全部或部分份额类别"限定的满足定义；
8. Q7/M3："有类别无字母"产品的 `class_count` 定义。

**B. 统计/评分口径（不影响引擎行为）**
第 3、16/17、18、19 项；以及 §39.4 的 scorer 处置顺序（先冻结 → 实测 → 单独裁定）。
