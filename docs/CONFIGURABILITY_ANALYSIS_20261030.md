# FundLex 配置化能力分析与建议（2026-10-30）

> 性质：**产品/技术分析建议，不是已实施功能，也不改变当前 NO-GO、未部署和“未获用户同意不跑真实模型”的状态。**  
> 依据：当前工作区 `codex/comprehensive-remediation-20261028`，HEAD `364dd2f`；只读源码、前端和已有文档，未调用真实模型、未改业务代码、未部署。  
> 关联记录：集中问题记录 **FL-D538**（“配置化能力缺口与分层建议”，状态为建议/未实施）。  
> **范围澄清（2026-10-30）**：本文中的“用户”指**普通业务使用者**（上传合同、审查修订、比对合同、维护自己的指引），不是组织管理员或运维。§4 中标记为 `[组织]`/`[运维]` 的项属于平台/管理员能力，不应出现在普通用户设置页；普通用户的优先范围以 **§11** 为准。

## 1. 结论摘要

1. **当前真正给终端用户的自助配置很少。** 设置页只有运行能力展示、修改密码和飞书绑定；指引页只有上传、解析、启用、恢复默认；新建任务页实际只让用户填任务名、选文件，指引固定使用“当前指引”，没有任务级业务选项。
2. **大量业务行为由环境变量和代码常量决定。** 运行代码直接读取至少 **58 个 `FUNDLEX_*` 环境变量**（不含 `LLM_*` 和动态角色前缀，且部分多行读取未计入），另有大量按 `G01-G22` 规则编号写死的策略、范围、交付分类和 DOCX 作者。普通用户无法改修订作者、文件名、交付策略、规则启停、排除基金类型等。
3. **“配置化”不等于“把全部环境变量做成输入框”。** 应分三层：个人偏好、组织业务配置、部署/运维配置；任务创建时再生成不可变快照。密钥、发布门禁、证据/写入边界、权限提升永远不能交给普通用户。
4. **最大价值不在 UI，而在规则执行元数据。** 当前 `generation/registry.py` 按 `G01-G22` 决定模板/拼接/删除/组合策略，`rule_scope.py` 和 `recall_pipeline.py` 也大量按规则编号写死行为。自定义指引即使换了业务文本，仍可能被内置 G 编号策略“绑架”（参见 FL-D439）。应把策略、范围、必需事实、保留策略做成**指引版本的可校验 sidecar 元数据**，而不是继续加全局开关。
5. **建议先做 10 个低风险高价值项**（见 §7.1），再逐步开放规则编辑、组织共享、模型预设和审批流。默认配置必须保持今天的行为完全不变。

### 2.4 已有可复用的安全模式

不要从零发明配置框架，项目里已有三个好模式：

1. **公开配置 allowlist**：`fundlex/guide_generation/service.py:24-72` 对成员可传字段做严格类型、范围、未知字段拒绝；`corpus_dir`、`vector_*`、`soft_max_*` 等运维字段直接禁止。这个 allowlist 目前已有 15 个整数字段、5 个布尔字段和 1 个列表字段，但前端只暴露 `corpus_limit` 和 `path_b_latest_only` 两个；说明部分后端配置化能力已经存在，缺的是产品化入口、权限和快照，而不是从零实现。这个模式应扩展到所有用户可配项。
2. **版本化 + 快照绑定**：指引版本、`rules_sha256`、任务 `guide_version_id/guide_rules_sha256` 已经保证“任务创建后指引变化不影响运行中的任务”。新配置也应沿用。
3. **密钥只记录存在性**：`ModelRoleConfig.safe_dict()` 去掉 `api_key`/`extra_headers`，只返回 `api_key_set`。设置页也不应回显密钥。

## 3. 建议的配置分层

| 层级 | 谁能改 | 作用域 | 典型内容 | 硬边界 |
| --- | --- | --- | --- | --- |
| **L0 代码不变量** | 不开放 | 全局 | 证据/来源/写入边界、发布门禁、文件安全、权限校验、数据隔离 | 任何配置都不能绕过 |
| **L1 部署/运维配置** | 系统管理员/部署方 | 整个部署 | 模型端点/密钥、数据库、对象存储、上传硬限制、并发、SSO/OIDC、Langfuse、feature flag | 只从环境变量/密钥系统读取；UI 只读展示“已配置/由部署锁定” |
| **L2 组织业务配置** | 组织管理员 | 组织/团队 | 共享指引、规则启停、排除基金类型、交付策略、修订作者、报告品牌、审批流、术语表 | 必须在 L0 边界内；变更需审计、版本化 |
| **L3 个人偏好** | 普通成员 | 本人 | 主题/密度、默认筛选、审核页默认视图、快捷键、通知渠道、默认下载命名 | 不影响合同正确性和组织策略 |
| **L4 任务覆盖** | 提任务的人 | 单个任务 | 规则组、输出产物、任务名/文件名、通知对象；指引版本在指引页维护 | 不得超过 L2 策略；创建时快照并写入报告 |

**按本次澄清的边界**：普通用户只直接使用 **L3 个人偏好 + L4 任务覆盖**；L2 中“自己的指引/自己的任务”可以开放给受信任业务用户，但组织级默认值、交付策略、排除清单、报告品牌、审批流仍由平台/管理员配置；L1 只做运维管理界面。

**优先级建议**：先做 L3/L4 的低风险项，再做 L2 的规则/交付配置，最后做 L1 的管理 UI。L1 的密钥类永远不要进业务设置页。

## 5. 不建议开放或只能受控开放的内容

以下内容即使“技术上能配”，也不应作为普通用户设置：

1. **密钥、数据库连接、模型端点、对象存储路径、语料路径**：泄露/越权/外发风险；只走环境变量或密钥系统。
2. **发布门禁、`auto_write`、证据/来源/写入边界、Claim Replay/最终查漏**：这些是“合同是否正确”的安全不变量，不能由用户关闭。
3. **权限提升/角色自授**：管理员才能改角色；不能让自己从 member 变 admin。
4. **任意 Prompt、正则、Python/脚本、规则执行代码**：会破坏 schema、证据链和可复现性；只允许受控的模板/元数据。
5. **把阻断规则静默改成“仅提示”**：会造成漏改却显示完成；只能进入“例外/未执行”并影响交付状态。
6. **按任务随意切换交付策略为更宽松模式**：应由组织管理员设定并审计；否则用户可以选择“更容易 complete”的策略。
7. **任意切换未审批的模型/端点**：只能选运维定义的预设；否则成本、合规、质量不可控。
8. **原地修改已发布指引**：必须生成新版本；运行中任务继续绑定旧快照。
9. **隐藏/删除报告中的失败、例外、证据**：报告可以精简展示，但原始失败和例外必须可追溯。
10. **跨 owner/组织读取配置或任务**：配置服务必须沿用现有 owner 隔离。
11. **算法阈值、相似度、候选/扫描上限、窗口大小等内部参数**：只应由运维/研发调整，不开放给业务用户；否则结果不可复现，也无法做版本验收。

一句话：**配置化的是“业务选择”，不是“安全证明”。**

## 6. 目标架构建议

### 6.1 数据模型

建议新增统一的设置表，而不是继续为每个功能加一张表：

```sql
CREATE TABLE app_settings (
    scope_type   TEXT NOT NULL,          -- system | org | user
    scope_id     TEXT NOT NULL,          -- 部署 id / org id / user id
    section      TEXT NOT NULL,          -- revision / delivery / report / notify ...
    schema_version INTEGER NOT NULL,
    version      INTEGER NOT NULL,       -- 乐观锁
    value_json   MEDIUMTEXT NOT NULL,
    updated_by   TEXT NOT NULL,
    updated_at   REAL NOT NULL,
    PRIMARY KEY (scope_type, scope_id, section)
);

CREATE TABLE app_settings_history (
    id           TEXT PRIMARY KEY,
    scope_type   TEXT NOT NULL,
    scope_id     TEXT NOT NULL,
    section      TEXT NOT NULL,
    version      INTEGER NOT NULL,
    before_json  MEDIUMTEXT NOT NULL,
    after_json   MEDIUMTEXT NOT NULL,
    changed_by   TEXT NOT NULL,
    changed_at   REAL NOT NULL,
    request_id   TEXT NOT NULL DEFAULT ''
);
```

任务表增加快照字段（沿用现有 `guide_version_id/guide_rules_sha256` 模式）：

```sql
ALTER TABLE tasks ADD COLUMN config_json   MEDIUMTEXT NOT NULL DEFAULT '{}';
ALTER TABLE tasks ADD COLUMN config_sha256 TEXT NOT NULL DEFAULT '';
```

指引表增加执行元数据 sidecar（或放在 `rules_json` 的顶层字段，但独立列更易校验/索引）：

```sql
ALTER TABLE guide_versions ADD COLUMN execution_json MEDIUMTEXT NOT NULL DEFAULT '{}';
ALTER TABLE guide_versions ADD COLUMN execution_sha256 TEXT NOT NULL DEFAULT '';
```

`execution_json` 建议包含每个 `rule_key`/operation 的：

- `default_tier`、`allowed_tiers`、`executor`
- `required_fact_status`、`required_components`
- `preserve_policy`
- `scope`：章节提示、正文/摘要副本、类别替换、槽位
- `condition`/`exception` 的语义类型
- `strictness`：阻断/例外/仅提示（受组织策略限制）

**不要**继续用 `G01` 这种展示编号作为行为主键；内置规则可以保留别名，但自定义规则要有稳定 `rule_key`。

### 6.2 解析优先级与快照

建议解析顺序：

```text
代码默认值
  → 部署锁定值（L1，只能运维改）
  → 组织策略（L2）
  → 用户偏好（L3）
  → 任务覆盖（L4，仅允许组织策略开放的字段）
  → 校验/裁剪（类型、范围、交叉约束）
  → 任务快照 config_json + config_sha256
```

规则：

- **部署锁定值**（如上传硬上限、允许的模型预设）不能被组织/用户覆盖；UI 显示“由部署锁定”。
- **组织策略**可以给默认值和允许范围；用户只能在范围内选。
- **任务覆盖**在创建时解析成有效值，并写进任务/报告；之后组织或用户改配置，不影响已创建任务。
- **密钥不参与合并**：只从环境变量/密钥系统读取，设置服务只保存变量名或 `configured` 布尔值。

### 6.3 校验、审计与迁移

- 每个 section 用 Pydantic/JSON Schema 定义；`extra="forbid"`，未知字段失败关闭（复用 `sanitize_public_config` 的思路）。
- 枚举、数值范围、字符串长度、文件名安全字符、路径禁止 `..`/绝对路径。
- 跨字段校验：例如“关闭某条阻断规则”必须要求填写理由，并在报告中列为例外；`strict` 策略下不允许关闭阻断规则。
- 乐观锁：`PATCH` 带 `If-Match: version`；冲突返回 409，不静默覆盖。
- 审计：每次变更写入 history；记录 actor、时间、前后值、请求 ID、原因（可选必填）。
- 迁移：`schema_version` + 显式迁移函数；旧配置读取时补默认值，不静默改写用户值。
- 回滚：按版本回滚；指引按版本链回滚/重新启用。
- 默认行为：所有新配置的默认值必须复现当前行为；发布前用“默认配置回归”证明没有行为变化。

### 6.4 API 建议

```text
GET    /api/settings/effective?task_id=...        # 返回有效值 + 来源 + 锁定标记
GET    /api/settings/schema                        # 前端动态表单/校验（可选）
PATCH  /api/settings/{scope}/{section}             # 带 If-Match/version
GET    /api/settings/history?scope=...&section=...
POST   /api/settings/{scope}/{section}/reset       # 恢复默认
POST   /api/tasks                                  # body 增加 config（allowlist）
PATCH  /api/guides/{version_id}/rules/{rule_key}   # 生成新版本，不原地改
POST   /api/guides/{version_id}/rules/{rule_key}/disable
POST   /api/guides/{version_id}/clone              # 组织共享/复制
GET    /api/model-profiles                         # 只返回名称/描述/可用性，不返回密钥
```

所有接口继续使用现有 `_user`/`_admin` 依赖和 owner 隔离；管理接口额外做角色校验。

### 6.5 前端信息架构

设置页建议从现在的“运行能力 + 飞书 + 密码”扩展为带权限的分组：

- **个人偏好**：主题/密度、语言/日期、默认首页、任务列表默认值、审核页默认值、快捷键、通知。
- **任务默认**：默认指引、默认输出、默认文件名、默认通知。
- **指引与规则**：当前指引、组织共享、规则列表、启停、编辑（新版本）、版本比较/回滚、发布审批。
- **交付与报告**：修订作者、报告品牌/免责声明、输出产物、例外策略、水印/密级（后期）。
- **通知与集成**：飞书、邮件/Webhook（后期）、事件订阅。
- **模型与质量**（管理员）：模型预设、角色路由只读、并发/限额只读、评测入口。
- **成员与权限**（管理员）：用户、角色、组织/团队。
- **系统与运维**（管理员，只读为主）：部署锁定项、上传限制、数据库/存储、版本信息。

每个字段建议显示：当前值、默认值、来源（系统/组织/个人/任务）、是否锁定、影响说明、恢复默认。危险项（关闭规则、放宽交付策略）需要二次确认 + 理由。

**前端版本注意**：当前 `FUNDLEX_FRONTEND_VERSION` 默认 `v1`（`fundlex/api.py:1401`），但 React V2 也在仓库中。配置必须由服务端提供，V1/V2 共用同一 API，不能只在一个前端实现，否则用户切换版本后配置“消失”。

### 6.6 安全与合规

- 设置读取按 owner/org 过滤；管理员跨组织查看需显式授权。
- API 响应、日志、报告、审计中都不出现密钥值；只出现变量名/`configured`。
- 配置变更写审计；高风险变更（规则启停、交付策略、权限）可要求二次确认或双人审批。
- 配置导入/导出只导出非密钥字段；导入时走同一校验。
- 备份包含设置表和 history；恢复后校验 schema/version。

## 7. 落地顺序建议

### 7.1 先做这 10 项（按普通用户澄清分为“用户可见”和“平台前提”）

1. **[平台前提] 统一设置基座**：`app_settings` + history + effective API + 任务快照。没有它，后面每加一个开关都会变成新的技术债。
2. **[用户可见] 修订作者/部门**：用户自己的显示名/作者名，任务可覆盖；直接解决 DOCX 里“资金清算部”千篇一律的问题。
3. **[用户可见] 输出文件名/ZIP 结构**：安全模板 + 服务端清洗；用户归档最直观。
4. **[用户可见] “我的指引”管理**：在现有指引页管理版本、启用/恢复默认；任务页不新增指引上传/选择入口。
5. **[用户可见] 个人默认值**：任务列表筛选/排序/每页条数、审核页/比对页默认布局、下载命名。
6. **[用户可见/P1] 规则组启停**：至少支持按组关闭；关闭项进入报告“未执行/例外”，不能静默。
7. **[管理员] 基金类型排除清单**：把 `FUNDLEX_RECALL_EXCLUDED_TYPES` 变成全局策略，带理由和证据要求；不放进普通用户设置页。
8. **[管理员] 交付策略/报告品牌**：管理员配置；报告显示策略和品牌；普通用户只读。
9. **[用户可见/P1] 运行时指引规则编辑**：复用法规生成的编辑/版本/审批模式，生成新版本。
10. **[管理员定义/用户选预设] 模型预设**：运维定义 fast/balanced/quality，用户只能选预设，不碰 endpoint/key。

### 7.2 分阶段

| 阶段 | 范围 | 主要交付 | 验收重点 |
| --- | --- | --- | --- |
| **P0 基座与快赢** | 设置表/API/UI 骨架、任务快照、修订作者、文件名、任务指引选择、个人默认值 | 默认行为不变；有效值/来源可见；审计可查 | 老任务/老配置完全兼容；无密钥泄露；快照可复现 |
| **P1 组织与规则** | org/workspace、角色权限、共享指引、规则启停、排除类型、交付策略、报告品牌、通知、审批流雏形 | 组织管理员可自助配置；普通成员只能选允许项 | 关闭规则/放宽策略必须进入例外；权限隔离通过 |
| **P2 引擎元数据与模型** | 规则 sidecar（tier/executor/facts/scope）、运行时规则编辑、版本比较/回滚、模型预设、Prompt 版本管理 | 自定义指引不再被 G 编号绑架；模型选择可控 | 自定义规则真实运行通过；模型/提示变更可回滚；评测隔离 |
| **P3 可选** | 水印/密级、SSO、API token、Webhook/邮件、多租户、条款模板库 | 按客户需求排期 | 安全评估/合规确认 |

### 7.3 每个阶段的“完成”标准

- 默认配置下，现有回归/真实任务行为与今天一致（先证明“不改行为”）。
- 配置解析有单元测试：默认值、层级覆盖、锁定项、非法值、跨字段约束。
- 权限测试：member 不能改组织/运维项；admin 不能越权读别的组织。
- 快照测试：同一任务重复解析得到相同 `config_sha256`；配置变更不影响已创建任务。
- 审计测试：谁、何时、改了什么、前后值、请求 ID 可查；可回滚。
- 端到端：用户改修订作者/文件名/规则开关 → 新建任务 → 真实 DOCX/报告体现 → 下载；管理员改组织策略 → 成员看到生效值和锁定提示。
- 安全：响应/日志/报告中无密钥；非法路径/未知字段失败关闭。

## 8. 需要产品确认的关键决策

1. **普通用户是否需要规则编辑权？** 已澄清“用户”是普通业务使用者；还需确认他们是只上传/启用/选择指引，还是也要直接编辑单条规则的文案、条件和例外。后者建议做成“高级/需复核”能力。
2. **单公司还是多公司/多团队？** 如果是多团队，需要共享指引/可见范围；如果单公司，可先做“我的指引”，避免过度设计。
3. **谁可以改交付策略和全局排除？** 建议管理员，普通用户只能只读；否则容易出现“为了 complete 而放宽策略”。
4. **是否需要审批流/双人复核？** 如果需要，配置项不只是“开关”，还要定义审批人、顺序、驳回、重新提交和审计。
5. **是否允许普通用户选择模型档位？** 建议只选管理员定义的预设；endpoint/key 永远运维。
6. **报告/合同是否需要品牌、水印、密级、保留期？** 这些往往由客户合规决定，建议组织级配置。
7. **配置变更是否需要重新跑评测/审批？** 规则/提示/模型变更应绑定版本和评测证据；纯 UI 偏好不需要。

## 9. 普通用户配置优先级（按 2026-10-30 澄清）

> 这里的“普通用户”指上传合同、提交修订、审查结果、比对合同、维护自己指引的业务人员；不是组织管理员或运维。普通用户设置页应尽量“少而直观”，高级/全局项放到管理员或运维。

### 9.1 第一阶段：普通用户设置页直接可见（P0）

| 配置项 | 为什么适合普通用户 | 边界 |
| --- | --- | --- |
| 显示名、修订作者 | 修订痕迹要显示“谁改的”；每个业务人员可设自己的作者名 | 组织可给默认值；任务可覆盖；写入 DOCX 和报告 |
| 当前/默认指引 + “我的指引”列表 | 用户已经在维护自己的指引；需要在指引页查看、启用、恢复默认 | **只在指引配置页操作**；任务页不新增上传/选择/切换入口；任务绑定当前指引快照 |
| 默认输出产物、文件名模板 | 用户最关心下载文件叫什么、包含哪些文件 | 模板只允许安全字符；报告/例外不能隐藏 |
| 任务列表默认筛选、排序、每页条数 | 高频个人习惯 | 服务端仍限制分页上限 |
| 审核页默认布局、显示已接受/拒绝、自动保存、快捷键 | 高频阅读习惯 | 不改变逐条选择结果 |
| 比对页默认视图、显示格式、忽略空白/格式差异 | 高频阅读习惯 | 差异判定仍以服务端为准 |
| 通知事件与渠道（站内/飞书） | 用户希望完成/失败/待复核时收到提醒 | 邮件/Webhook 需运维先配置 |
| 默认任务名、默认任务模式（交付/仅诊断/试运行） | 用户可能需要“先看问题、不改文件” | 评测/诊断结果必须标注，不能当正式交付 |
| 报告详细程度（摘要/完整证据） | 用户可以选择下载版式 | 原始报告中的失败/例外必须保留，不能隐藏 |
| 自己的指引管理：上传、解析、启用、重命名、查看版本 | 已有能力，补上“我的指引”视图 | 删除/共享需谨慎；运行中任务绑定旧版本 |

### 9.2 第二阶段：普通用户任务级业务选项（P1，需产品确认）

| 配置项 | 价值 | 建议边界 |
| --- | --- | --- |
| 规则组/单规则启停 | “本轮只改费用条款”或临时关闭某条规则 | 关闭项必须进入报告“未执行/例外”；不能静默当完成 |
| 正文/摘要/两者 | 有些合同只需要改正文或只需同步摘要 | 做成预设并给出风险提示；底层仍按规则 scope 校验 |
| 输出产物选择 | 只要修订版、只要最终版、或含报告 | 例外清单/失败原因不能省略 |
| 指引规则编辑 | 用户发现指引文案/条件不适合自己的合同 | 只编辑“自己的指引”，生成新版本；已发布/运行中版本不改 |
| 指引版本比较/回滚 | 用户自己维护多版指引 | 复用法规生成的版本 diff/审批模式 |
| 模型质量档位 | 用户希望“快一点/稳一点” | 只在管理员定义好 fast/balanced/quality 预设后选择；不暴露 endpoint/key |
| 任务通知对象 | 把完成/待复核通知给同事 | 只允许选本组织/本任务可见成员 |

### 9.3 不建议放进普通用户设置页

| 项目 | 原因 | 应放在哪里 |
| --- | --- | --- |
| 交付策略 `strict/review_assisted` | 直接改变“什么算 complete”，选宽松策略会掩盖漏改 | 管理员/组织策略，普通用户只读 |
| 整份排除基金类型 | 全局业务范围，误配会整类合同不处理 | 管理员/组织策略 |
| 报告品牌、水印、免责声明 | 公司法务/品牌统一管理 | 管理员/组织配置 |
| 模型 endpoint/key、Prompt、算法阈值 | 安全、成本、可复现性 | 运维/研发 |
| 角色权限、SSO、上传硬限制、保留期 | 安全/合规 | 运维/管理员 |
| 任意规则执行策略/脚本 | 会破坏证据链和可复现性 | 平台高级配置，需审批 |
| 审批流定义 | 组织流程，不是个人偏好 | 管理员；普通用户只看状态 |

### 9.4 给普通用户配置也必须有的保护

- 关闭规则、改指引、改输出，都必须**写入任务快照和报告**，不能只存在浏览器里。
- 关闭的规则要显示为“未执行/例外”，不能把结果标成完整。
- 指引编辑必须生成新版本，运行中的任务继续用旧快照。
- 默认值必须复现当前行为；用户不改配置时，结果和今天一致。
- 所有“危险项”（关闭规则、切到仅诊断、改指引新文）要有明确提示和二次确认。
