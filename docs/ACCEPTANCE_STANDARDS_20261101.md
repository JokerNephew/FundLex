# FundLex 验收标准总册（2026-11-01，总指挥定标，全体验证方共用一把尺）

> 用户指令（原话）：「不一定每个非要你亲自检查，你安排好对话或者子agent去检查也行，但是你得说清楚验收的标准」
> 分工：总指挥=定标准+抽验≥20%+终审放行；**实现者不得自验**（任何 FL 的验收必须由另一条线按本册执行）；监督线=常驻验收执行+对验收者再审计。

## S1 界面类（文案/样式/布局/交互/信息架构）
每条 FL 销号必须同时具备：
1. **用户原话断言表**：把用户那句话拆成可判真假的断言，逐条 ✅/❌（例：「查看是红字无框」→ 生产两列表的查看按钮 computed style 一致）。
2. **生产证据**：页面截图（修复后）+ 关键元素计算样式值（字重/字号/边框/颜色/时长），与断言一一对应；纯代码 grep、单元测试绿、构建成功**均不构成验收**。
3. **同类清零**：该问题族在生产全站（V1+V2+深口子页面/弹层/状态态）grep+抽查截图证明无同类残留。
4. **双盲**：由非实现线验收（对照实现者给的「改动清单」之外自行找茬）。

## S2 引擎/评测类
1. fc=0（硬门）、wrong=0；完成率、actual=reported 逐案一致。
2. 评分必须读**实际产物 DOCX**；修复命中须病灶真实复验（指定合同指定义务）。
3. 机制面证明：改动落在通用抽象层，无规则级/样本级特判（diff 审查+mutation 反例）。
4. 历史如实留史：各轮成绩并排，不覆盖不冒充。

## S3 代码审计类
1. 覆盖矩阵逐格签认：✅+「无发现」或发现编号；抽样/跳格=该格未完成。
2. 发现分级：可直修/需裁决/需用户定，处置状态可追溯。

## S4 发布放行类（每次发布必过）
1. 全量回归绿（含新测试）；冲突裁决记录在案。
2. 生产指纹核验：部署产物与声称内容逐一对应（文件 hash/grep/HTTP 200）。
3. **真实用户路径走查**：登录→实际操作→产物下载核对，由非实现线执行并留截图。
4. 已知缺陷清单随发布声明：不冒称已修。

## 抽验规则
- 主线对每条 FL 的验收证据不低于 20% 随机复核；发现一次证据造假/夸大，该验收者的全部历史验收降级重验。
- 用户随时抽查：任何一条验收证据必须能当场重放（截图/文件/命令行）。
