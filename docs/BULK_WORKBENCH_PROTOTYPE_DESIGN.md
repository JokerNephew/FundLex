# 大批量合同工作台：第一阶段 HTML 原型设计

日期：2026-10-13。范围仅为 `workbench/` 下的离线交互原型；正式 `frontend/`、API、规则开关、运行数据均不改动。原型数据明确标为示例，不上传合同、不调用模型。

## 产品诊断

主要用户是基金公司的合规、产品与运营人员。典型任务是一次准备数百份 DOCX，检查可接收文件，提交整个任务，持续查看任务总进度，集中定位排除、失败与不完整结果，阅读证据并下载报告。完整路径是“选择文件／文件夹 → 提交前检查 → 提交任务 → 观察任务总进度与逐合同状态 → 按资格、处理状态、交付完整性和原因定位 → 看逐合同证据 → 下载逐合同报告和任务汇总”。

现有正式页把新建批次、批次列表、当前批次、合同结果与详情堆在同一长页面；批次入口缺少大量文件的预检查，文件选择会被再次选择覆盖。批次列表只有基本状态，无搜索、排序、分页与大规模任务关联。结果表没有筛选，长文件名、长证据、原始哈希与错误码挤占业务视线。批次完成、资格符合和交付完整的层次虽然有字段，但在总览中仍容易被读成同一种“成功”。开发身份输入占据顶部业务区域。

业务首屏应呈现任务规模、任务总进度、异常数量、资格及交付状态、下一步可执行操作。源文件哈希、内部 ID、规则哈希、英文错误码、模型阶段细节进入展开的技术与证据区。失败原因使用准确中文解释，保留原始码。不能出现人工复核、审批或待办语义。

2026-10-13 用户补充确认：左侧导航固定；单批数量限制属于技术层面，不放入用户流程；进度与合同结果均按整个任务展示。因此“任务”是业务信息架构中的统一工作单位，底层批次只用于服务端传输和调度。

## 页面架构与关键交互

1. **任务总览**：办公软件式固定左侧导航与全宽工作区。呈现任务名称、规模、总进度、异常提示和“新建批量任务”；进入任务后共享同一组合同数据。“处理完成”只表示任务内所有合同都已结束处理。
2. **批量导入**：多文件、拖拽和文件夹选择均进入同一临时清单；可继续追加。展示总数、总大小、可接收数、异常数；按名称搜索和按“全部／可接收／异常”筛选、分页、移除与清空。非 DOCX、单文件超 25 MiB、文件名与大小相同的疑似重复分别标注，异常文件不进入模拟提交。右侧是任务提交前检查与本次规模，底层拆批对用户透明。文件选择、上传完成、合同处理完成分为三个不同阶段。
3. **处理进度**：整个任务的总数、已上传、排队、处理中、已处理、失败关闭数量与总进度同屏呈现；可查看逐合同状态。暂停和继续作用于整个示例任务；单份失败仍显示其他合同继续。原型按钮只改变示例状态，正式任务控制需要后端任务编排能力。
4. **合同结果**：按当前任务全部合同的资格、处理状态、交付完整性、失败原因筛选，并提供文件名局部搜索、排序与分页。筛选范围明确是“当前任务的示例合同”。逐合同详情展示业务结论、中文原因、资格证据、规则动作、报告入口；技术折叠区保留内部 ID、哈希、原始错误码。用户无需切换底层批次才能定位异常。
5. **交付**：逐合同 JSON/Markdown 报告是现有能力；任务汇总在原型中演示，正式版本需服务端聚合各底层批次报告。仅实际存在且通过完整性校验的最终版/修订版 DOCX 才能作为合同下载。当前 22 个 action 自动写入全部关闭，示例中的“资格符合”不能转译为“可直接使用”；原型不得展示可下载的最终合同。排除与失败关闭为未生成，不完整为不可直接使用。
6. **开发设置**：本地开发身份放在单独设置区，并标明非生产登录；原型不建立真实身份会话。

视觉沿用 `08-fluent-office.html` 的广发基金标志、橙红强调色、浅灰工作区、清晰边框与高密度办公表格。桌面侧栏固定在顶部栏下方至视口底部，工作区滚动时导航位置不变；侧栏内容超出时独立滚动。笔记本收缩侧栏，手机使用固定顶部导航并保留文字标签；按钮、徽标、空态、焦点和长文本使用统一设计变量。键盘可操作筛选、分页、打开/关闭详情，弹层具备焦点管理。页面本身不横向溢出，局部宽表允许容器内滚动。

## 原型示例与实现边界

原型预置明确标注的 368 份示例合同，覆盖进行中、暂停、完成、资格符合、类型排除、失败关闭、交付不完整与未生成。示例统计由示例记录计算，不宣称真实处理结果。上传、暂停、继续、下载按钮均只演示对应界面和提示；下载模拟的仅为示例报告文本，不是后端产物。原型可选择本地文件以体验预检查，但不读取合同内容、不发网络请求。

真实 API 当前提供 `GET/POST /api/batches`、批次详情、暂停/恢复、逐合同报告与四种按合同授权的下载、批次 Markdown 汇总；通过 `X-FundLex-User` 做本地开发身份隔离。默认上限为每批 20 份、每文件 25 MiB、每批 50 MiB。此约束仅留在开发文档中，业务 UI 不显示拆批数量或传输限制。正式实现任务层体验还需后端确定/提供：持久任务实体、底层批次关联与提交幂等编排、任务整体暂停/恢复与部分操作失败回执、任务聚合进度和合同查询、服务端搜索/筛选/排序/分页、任务汇总报告、可恢复或可观测上传进度、逐文件接收结果、批量结果打包下载及生产身份。前端可对当前任务已加载的合同做局部筛选，必须明确作用域；不得将浏览器内存中的批次关联作为可跨设备持续恢复的任务能力。容量、队列吞吐与生产多 worker 尚未验收。

## 原型验收

使用真实浏览器检查 368 份示例的任务总进度、任务全部合同搜索、筛选、排序、分页、详情、异常文件、提交前检查、任务暂停/继续、示例报告下载和键盘操作；检查滚动后侧栏位置不变，检查桌面、笔记本、手机视口，无页面级横向溢出或控制台错误。正式 API 的 DOCX 上传、身份隔离和实际报告下载验收留到获准修改正式前端的第二阶段；第一阶段不以示例交互充当真实端到端验证。
