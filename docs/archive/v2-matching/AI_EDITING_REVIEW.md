# AI 局部修改方案：三个子 agent 评审汇总

日期：2026-10-13。评审对象：`AI_EDITING_DESIGN.md`，设计提交 `3e0cd09`。用户明确授权开启子 agent 评价方案；三个评审均使用 gpt-6.1-sol，分别检查业务、工程和评测，仅只读源码和资料。未调用合同处理模型、运行样本、修改运行状态或启用自动写入。

## 结论

方案适合开展受控的实际修改试验，当前仍属于方向性设计。未具备自由生成文字的正式交付证据；还不能承诺多数合同可以自动改完，也不能根据模型两次一致就认定正确。

判断自动化是否有用，需要同时公布正确修改率和完整自动交付率。大量拒绝可以降低误改，但不能算功能已经可用。报告供追溯；逐合同交给用户批准不作为解决方案。

## 三个评审的主要判断

| 评审 | 判断 | 核心依据 |
| --- | --- | --- |
| 业务 | 局部生成可试验；正式交付前必须明确语义支持范围 | 已提取事实核验无法发现漏提的限定或例外；各 action 尚无完整语义契约 |
| 工程 | 可复用 DOCX 编辑器；生成、验证、计划和下载接口都需改造 | 现有 ModelGateway 禁止生成文字；固定模板与正式产物边界贯穿流水线 |
| 评测 | 旧定位指标不足以证明实际修改正确 | 旧评分器不读取修改文件，16份是修复集，全部拒绝不能证明端到端有效 |

## 必须优先补齐的六项

### 1. 核验已提取事实，不能证明没有遗漏

设计第55行核验“其余提取到的事实”。如果生成器和检查器都漏提某个渠道限定或例外，该项根本不会进入核验。`content_verified` 不应被解释为全部业务含义已被确定性证明。

每个 action 须明确：代码能验证的字段及关系、模型判读项、支持的语言和结构范围、尚不支持的表达、未知与拒绝条件。对于支持范围内的修改，使用经过评测的质量证据；不能把没有发现问题当成证明无问题。

### 2. 每条规则需要完整的业务契约和依赖证据

设计第25—33行还没有具体 action 的字段 schema。以 R10 为例，承担主体、收取时点、归属关系应分别列出；旧条款中的期限、比例、费用用途及类别限制，哪些允许删除必须有指引依据。取消固定文字限制不能代替确认这些业务要求。

引用前款、类别定义、费率表或渠道条件时，要声明依赖检索范围。依赖缺失或冲突则失败。正文与摘要需要对整组修改后的视图核验；逐条通过不保证组合后没有矛盾。

### 3. 位置存在与唯一，不代表所有应改目标已找到

代码可以证明候选引文真实、唯一、可写；不能据此证明无漏召回。须独立盘点规定业务章节中的目标，并与计划对账，区分正确修改、已符合、未知、结构不支持和漏改。未命中不能自动记为已符合。

当前 R10 的 paragraph scope 会扩为整段（`fundlex/rules.py` 第795—807行附近）；新定位应枚举指定位置中的精确引文，以有来源的前后文消歧，恰好一个才执行。末尾空格策略预先登记；不回退到首次 find。相邻或重叠编辑维持明确拒绝，不能临时拼接已经独立验证的文案。

### 4. 生成验证的来源及执行权需要重新设计

现有 `fundlex/model.py` 第100行限制 task，第116—118行禁止写入文字。第164—172行只校验引文出现在整个上下文；当上下文包含源文、规则和生成文字时，这不足以证明引文来自合同。

新增任务及证据 schema，使用 source_id、role、location、quote 到对应源片段核对。由服务端形成绑定源文、规则、生成文字和验证事件的记录；模型自填 verified 不能获得执行权。现有 `fundlex/docx.py` 第637行的模板相等应改为明确的生成内容来源校验，不能通过临时模板字典规避。

### 5. 评测模式必须贯穿持久化和下载

当前 `fundlex/pipeline.py` 第179—187行 evaluation 只是零修改副本；worker、store、API 仅支持正式四类产物，且不完整结果不开放正式 DOCX。需要服务端持久化 execution_mode，绑定任务身份、检查点、计划和产物；新增经过校验的评测 DOCX kinds 与独立下载入口。文件名或界面标签不能充当隔离边界。

模型输出、验证、冻结计划的续跑需分别保存状态。目标是同源与同依赖复用同一已核验计划、当前 fencing token 发布一次；重复运行生成不同修订时间不能冒称字节幂等。预算耗尽不应不断占用普通 worker 重试次数。

### 6. 新评测必须检查实际文件与业务结果

`tools/evaluation/pilot_compare.py` 第122行附近评分定位和报告标志，没有核对改后 DOCX 及义务保留。原 gold 的坐标校验只证明引文存在，尚不能证明其业务真值得到外部确认。

新标签在生成前冻结：指引要求、适用性、全部应改位置、授权变化、必须保留条件和非目标区域。允许多种正确文字表达，不用旧模板逐字相等评分。AI 参考标签仍如实标识，含糊业务政策不靠多模型投票决定。

## 推荐的最小落地顺序

1. 优先写重点 action 的有限语义契约及拒绝条件，并实现混合段精确定位。
2. 增加带来源角色的生成/验证任务、服务端验证记录及整组一致性检查。
3. 接通冻结计划、双产物、评测持久状态与独立下载；保持正式交付边界。
4. 登记预算后先1—2份真实非空修改，再运行已有16份，必须包含 R10 实际生成新文；仅做删除不能证明生成能力通过。
5. 预选6—8份未参与修复的 DOCX，以及已知答案的主体互换、否定、条件遗漏、单位错误等夹具。报告修复集、未见集和夹具各自结果，不恢复取消的284份。

## 客观验收指标

- 编辑精度：正确实际编辑数 / 全部实际编辑数；单列严重误改。
- 端到端目标完成率：正确实际编辑数 / 全部应修改目标；拒绝、漏改及不支持继续进入整体完成率分母，另报支持子集。
- 保留要求满足率：满足的必须保留要求 / 全部必须保留要求。
- 完整自动交付率：业务与文件检查均正确完成的合同 / 全部应处理合同；同时公布拒绝和失败原因。
- 错误新文接受率和合法改写拒绝率，使用事先确定答案的变异夹具评价检查器。
- 非目标变化、错误事实新增/丢失、正文摘要冲突、修订等价失败的数量。

编辑精度的分母不包含没有执行的拒绝项，目标完成率和自动交付率必须包含。避免把“无误改但全部拒绝”描述为通过。

旧严格范围分数保留，另列纯空白差异与实质性多删/少删。评分器 overlapping 减 located 的候选集合口径不同，存在潜在负值风险；需在后续评分改造中验证和修复，本次只静态发现，未实测复现。重复候选与计划冲突也要单列。
