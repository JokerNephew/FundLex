# 直通解析与合同修改重构评估（2026-11-02；静态审查，未施工/未验收）

## 用户已确认的产品契约

1. 指引 DOCX 和合同 DOCX 不含表格；指引按章节解析成无槽位、自然语言条件的原子规则卡，分支实例化；不因旧式文字/认证/质量门拒绝可用卡。
2. 合同只修改指引对应章节和该事项对应的摘要；目录用于选章节、不能授权全文修改。目标范围内让模型枚举全部候选、逐句生成写回、局部补扫；优先召回，不要求与指引文句逐字一致。
3. 保留输入原有修订痕迹并叠加我方痕迹，可独立接受或拒绝；交付实际最终版、痕迹版与真实改动对照；不向用户派人工核查，不在交付物列未决，也不显示“未经校验”。
4. **每份合同**：实际成功写回至少一处且最终文件可授权下载 => “完成”；零处实际可交付修改 => “未完成”。完成不声称全规则命中。模型无费用门禁；保留物理资源/限流/失败有限重试。

## 必须保留或重用的主功能（不可随旧引擎一键删除）

- 登录/归属、上传格式与包安全、存储与持久任务、幂等/重试/租约/隔离/模型配置：`fundlex/api.py`、`application/task_service.py`、`tasks.py`、`store.py`、`jobs.py`。新上传指引当前不会自动替换现用版本（`guide_store.py:390-427`、`api.py:1107-1118`），需要显式实现“解析成功→该用户后续任务默认使用”且不修改已绑定任务。使用者手选其他指引的入口仍应可用。
- DOCX 结构/编辑位置/来源哈希/非目标位置不变、`generate_artifacts` 输出 final+redline 并记录真实 manifest：`fundlex/docx.py:889-983,1547-1648`。旧 `validate_edit_plan` 对生成文字要求 `content_check`，重构为仅校验生成记录/写入来源与几何，不用旧“新文与指引逐字一致”的业务门；不能跳过范围保护、文件结构或无改动判定。
- 原有修订痕迹独立保存与选择修订：`fundlex/docx.py:1573-1617`、`fundlex/selective.py:242-279`、`fundlex/api.py:1601-1633`。保留 manifest/外部原修订清单格式供修订审阅；新最终版如存在原修订，其语义须按真实文件核对，不能仅凭 UI 断言独立可拒绝。
- 下载需要 worker 持久产物、报表/文件配对哈希一致、身份授权：`fundlex/jobs.py:340-444`、`fundlex/store.py:276-323,930-1054`、`fundlex/tasks.py:842-865`；应为新报告 schema 增加完整的有效交付契约，而非把 `working_*` 强制改名为 `final` 或关掉 hash/身份门。
- 指引版本不可变、历史任务绑定及历史报告/修订下载；`fundlex/tasks.py:104-149` 的快照、`jobs.py:290-305` 的 engine build/schema 限制禁止新代码静默改跑旧排队任务。旧报告必须仍能读、旧下载按旧报告契约服务；新任务按新报告/引擎版本，不用旧逻辑夹心运行。
- 任务结果 ZIP、结果总览、CSV 与飞书发报告的用户出口；其他独立业务“法规生成指引”和“合同比对”不应随之删除。

## 关键风险及防范

1. **“一处成功”的真值**：`frontend/app.js:870-882`、`fundlex/edit_summary.py:64-68` 使用 plan/target 计数；写入器可能跳过某条。新引擎必须持久化已重开 DOCX 的修订 manifest 和实际前后差异，按实际可下载的文件计数。单份成功不能推断全部已改。
2. **多路兜底越界**：`recall_pipeline.py:1158-1168` 有跨章节“完全相同段落副本”扩域；新引擎只允许目标章节+该事项对应摘要，任何搜索/重试/补扫在写回边界再次检查物理位置。
3. **已改部分又异常**：`jobs.py:442-444` 可能因资格或错误码标 job failed；`recall_pipeline.py:4467-4495` 在异常时把 final 降 working。新逻辑应在单点故障后继续其他卡，待产物完整写回后按 >=1 判定；文件整体不可读或无有效写回才未完成。模型 transport 可有限自动重试，不可无限空转。
4. **报告泄出未决**：批量 ZIP 已排除技术 `report_json`/`report_md` (`api.py:1503-1508`)，但单份报告、任务总览与 CSV、飞书仍暴露旧文案；需要把内部日志与用户交付报告分离，不改变身份权限。
5. **物理删除次序**：旧 parser/engine 被 `guide_generation/engine_compat.py`、stage replay、旧测试调用；先迁移/隔离调用者与历史读路径，再删除不被新主路径依赖的旧业务代码。不要删除前端 V1 唯一工作台、`docx.py` 或 compare 模块。
6. **逐句模型调用容量**：`fundlex/model.py:216-242` 默认 `FUNDLEX_MODEL_MAX_CALLS=16`、`FUNDLEX_MODEL_CONTEXT_CHARS=12000`，是否实际阻断取决于 `FUNDLEX_MODEL_ENFORCE_LIMITS`；逐段召回/改写不能假定一次调用可无限列出所有候选。须按章节分片、限制单次上下文并设有进展的分片续跑，保留供应商并发/物理资源约束；成本账本仅观测，不设费用门槛。未核对当前生产的 enforce 配置值，不宣称线上已命中该限制。

## 派工勘误（2026-11-02，用户纠正；非实现完成）

此前给解析线与定位/改写线的 prompt 写了“不要修改旧文件”，本意是并行时暂时划定文件所有权，措辞不当，容易造成只添新代码、旧业务保留到交付的错误结果。最终要求是**完成入口切换及历史/外部依赖迁移后，物理删除旧槽位/认证/注册门、旧义务矩阵/逐层审计覆盖/未决人工业务实现和用户侧文案**，而不是仅以新模块遮蔽旧逻辑；旧代码不能在新路径上作为 fallback。与之不同，身份权限、持久任务、DOCX 包完整性/真实写回/修订分层、授权下载/哈希这些基础能力要保留并迁入新路径。删除工作由负责旧模块的独立收口线统一认领，在各施工线的隔离分支分别切换和清理并经依赖检索/历史数据兼容验证后才合并，不得抢改其他在施工分支或趁新路径未可用先删运行依赖。若旧业务仍有在途任务/历史 API 引用，须明确迁移或最小只读读取兼容，不能静默把旧任务按新规则执行。
